<objective>
Record how the review-code description routes against the user's installed review skills (PKG-03, roadmap success criterion 4).

Purpose: roadmap criterion 4 requires the description to trigger on should-trigger review prompts and stay silent on should-not-trigger prompts. D-04 aims to win every code-review ask, including over the installed critical-code-reviewer; D-05 requires recording which skill wins per prompt and flagging every loss; D-06 fixes the method as a hand-checked table of about 10 should-trigger and 10 should-not-trigger prompts, with no eval harness. Routing is model behaviour, so the table is an observation, not a guarantee.
Output: docs/trigger-prompts.md with a complete result table and a user disposition for every flagged row; SKILL.md changes only if the user chooses to tune.
</objective>

## Alternatives Considered

- **Hand-checked interactive trials (D-06)**: routing follows the always-loaded skill description per https://code.claude.com/docs/en/skills (read 2026-10-17); observed in the user's real skill set, which is the collision surface.
- **claude plugin eval trigger cases**: built-in behavioural suite per https://code.claude.com/docs/en/plugin-evals (read 2026-10-17); deferred in 01-CONTEXT.md.
- **Headless claude -p runs with stream-json**: automatable, but the live probe in `01-RESEARCH.md` Collision Surface (2026-10-17) showed the user's session hooks take the first action, so the routing decision was never observed.

Decided by: simplicity (no harness to build); D-06 locks the manual method.
